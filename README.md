# MiniMax-H3 on Tesla V100 — Reproducible Deployment Recipe (stable-diffusion.cpp + GGUF)

> Status: **✅ Verified end-to-end on a single Tesla V100-PCIE-32GB (Volta / sm_70)** — video **and audio** in one pass.
> Measured capability (Sept 2026): production canvas **1344×768, up to 209 frames (8.71 s) per shot**; 1024×576 up to **243 frames (10.12 s)**; 1920×1088×39 verified. Full data map: [`docs/resolution_duration_guide.md`](docs/resolution_duration_guide.md).
>
> ⚠️ **If you read this repo before 2026-09-29**: two of its conclusions were wrong and are now fixed (see **Corrections** at the bottom). Short version: run with `--diffusion-fa --offload-to-cpu --mmap`, and do **not** pass `--backend` / `--params-backend`.

This is a **how-to / deployment recipe**, not a new model or framework. It packages the
working path for running [MiniMax-H3](https://github.com/wildminder/awesome-minimax-H3)
on an NVIDIA **V100 (sm_70)** — plus the measured cost of every resolution × duration
combination we run in daily production.

## Why this exists

- ComfyUI's **default** H3 route (0.33.2 + comfy-kitchen + T8 + v100-patch) does **not**
  work on V100 (`cudaErrorNotSupported` / OOM) — we confirmed this ourselves.
  **Update 2026-09-18:** a non-default ComfyUI route *does* work (fp8_scaled DiT +
  nvfp4 encoders + the `ComfyUI-MiniMaxH3-FP16Safe` plugin + an eager-execution patch);
  it runs 3–6× slower than sd.cpp, so sd.cpp remains our production stack — but
  "impossible on V100" was wrong. Details in [Corrections](#corrections--what-we-got-wrong-at-first-2026-09-29).
- V100 (Volta) has **no bf16 / fp8 / int8 tensor cores** — only fp16/fp32. That costs
  *throughput*, not correctness: the fp16/fp32 compute paths in this stack produced zero
  NaN / corruption issues across three weeks of daily production.
- The working route is **stable-diffusion.cpp + GGUF** — sd.cpp natively supports H3,
  and quantized GGUF + `--offload-to-cpu` fits the whole ~35 GB model set on a 32 GB
  card (weights live in system RAM; VRAM only holds activations).

## The recipe (short)

1. **Compile sd.cpp with CUDA for sm_70** (must build from source; prebuilt PTX breaks on V100).
2. **Download the 4 model files** (diffusion model + text encoder + 2 VAEs), optionally
   the Turbo LoRA for a 2.5× sampling speedup.
3. **Run with `--cfg-scale 1.0 --diffusion-fa --offload-to-cpu --mmap`** — do **not**
   pass `--backend` / `--params-backend` (they override offload and disable auto-fit;
   see Corrections #1).

Full steps, exact commands, and gotchas are below / in `examples/run_command.md`.

## What worked (measured)

One Tesla V100-PCIE-32GB, Q4_K_M GGUF, 24 fps, video + audio in one pass.
"8 + LoRA" = 8 steps with the Turbo distillation LoRA (multiplier 1.0) — our production default.

| Run | Config | Sampling | End-to-end |
|---|---|---:|---:|
| 256×256×5 | 8 steps | — | 135 s *(2026-09-07, pre-FA)* |
| 864×480×56 (the demo above) | 8 steps | — | 687 s *(2026-09-07, pre-FA)* |
| 1024×576×56 (2.33 s) | 8 steps | 253 s | 311 s |
| 1024×576×124 (5.17 s) | 8 + LoRA | 688–715 s | 793–817 s |
| 1024×576×243 (10.12 s) | 8 + LoRA | 1,666 s | 1,890 s |
| 1280×720×39 (1.63 s) | 8 steps | 279 s | 331 s |
| 1536×864×39 (1.63 s) | 8 steps | 425 s | 496 s |
| 1920×1088×39 (1.63 s) | 8 steps | 762 s | 855 s |
| 1344×768×158 (6.58 s) | 8 + LoRA | ~2,100 s | ~38 min |
| **1344×768×209 (8.71 s) — measured ceiling** | 8 + LoRA | 3,224 s | 60 min |

Memory behavior with `--offload-to-cpu`: all ~35 GB of weights sit in system RAM
(0 MB VRAM resident); the generation peak is activations only — 15.8 GB at
1024×576×56, and 32.2 GB (the card's limit) at 1344×768×209.

Three more measured facts worth knowing:

- **`--mmap`** cuts cold-start end-to-end **4.3×** (1236 → 286 s) with **bit-identical**
  output. Same-seed re-runs are bit-identical in general, so A/B testing is clean.
- **Cost model** (validated to ~2%): sampling time ∝ `pixels × frames^1.2`, peak VRAM ∝
  `pixels × frames`. You can predict OOM risk and runtime *before* launching anything.
- **Per-step time is independent of step count** (8 steps: 32.3 s/step; 20 steps:
  32.4 s/step at 1024×576×39), and sampling pins the card's 250 W power cap — the
  workload is compute-bound, not transfer-bound.

Full resolution × duration map, the 768p VRAM boundary table, speed-lever verdicts
(what worked / what visibly broke) and production gotchas:
**[docs/resolution_duration_guide.md](docs/resolution_duration_guide.md)**.

## The gotchas (the actual value of this repo)

- ✅ **`--diffusion-fa --offload-to-cpu --mmap` together** — the official sd.cpp pairing
  for H3. Flash attention breaks the frame wall (1024×576: 39 → 243 frames); offload
  costs only ~1.7% and frees ~16 GB of VRAM; mmap fixes cold-start I/O.
- ❌ **Do NOT pass `--backend` / `--params-backend`** — an explicit module assignment
  overrides `--offload-to-cpu` and disables `--auto-fit`. This combination is what
  caused our original "offload is extremely slow" misdiagnosis (Corrections #1).
- ✅ **`--cfg-scale 1.0` is mandatory** — the default 7.0 makes H3 abort immediately.
- ✅ **Frames on the `17k+5` grid** (5, 22, 39, 56, 73 … 124, 158 … 209, 243);
  width/height multiples of 32 (a 1280×720 request renders as 1280×736).
- ⚠️ **Turbo LoRA needs a key-name conversion for sd.cpp** — the original HF safetensors
  loads with *zero effect and zero errors* (silent no-op). Convert once with
  [`tools/convert_h3_lora.py`](tools/convert_h3_lora.py) (mode `mm`), then reference it
  in the prompt as `<lora:minimax_h3_turbo_v4_step600_ema_sdcpp.safetensors:1.0>` with
  `--lora-model-dir` set. **8 steps is the quality floor** (4/6-step output was rejected
  on quality by eye; the LoRA author's own usable range is 4–8).
- ⚠️ **Audio is written as PCM inside WebM**, which players silently ignore — remux
  before delivery (`-c:v copy -c:a libopus` for webm, or re-encode to mp4 / h264+aac).
  Also, runs without the Turbo LoRA came out near-silent in our tests — keep the LoRA
  on, or explicitly describe the sound in the prompt.
- ✅ `-DSD_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70`; build from source.
- ✅ CUDA bin (`...\CUDA\v12.4\bin`) must be on PATH at runtime, else the exe fails with
  error `0xC0000135` (DLL not found).
- ✅ `git clone --depth 1` does NOT pull submodules — run `git submodule update --init --recursive`.

## Prerequisites

- NVIDIA **Tesla V100-PCIE-32GB** (sm_70), driver ≥ CUDA 12 compat.
- Windows + **Visual Studio Build Tools** (MSVC), **CMake**, **CUDA Toolkit 12.x**, **ninja**.
- ~128 GB system RAM recommended (the offload path parks ~35 GB of weights in RAM).

## Build (see `build_sdcpp.bat`)

```bat
cmake -G Ninja -B build -DCMAKE_BUILD_TYPE=Release -DSD_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70 ^
      -DCMAKE_CUDA_COMPILER="<CUDA>/bin/nvcc.exe"
cmake --build build -j 12
```
Output: `build/bin/sd-cli.exe` (and `sd-server.exe`).

## Run (see `examples/run_command.md`)

```powershell
set PATH=<CUDA>\bin;%PATH%
sd-cli.exe -M vid_gen ^
  --diffusion-model <main.gguf> --vae <video_vae> --audio-vae <audio_vae> --llm <encoder.gguf> ^
  -p "<prompt>" --cfg-scale 1.0 ^
  -W 1024 -H 576 --video-frames 56 --fps 24 --steps 8 --rng cpu ^
  --diffusion-fa --offload-to-cpu --mmap ^
  -o out.webm
```

Verify the backend:
```powershell
sd-cli.exe --list-devices   # expect: CUDA0   Tesla V100-PCIE-32GB
```

(The demo spec, the Turbo-LoRA variant, and chaining for longer films are in
[`examples/run_command.md`](examples/run_command.md).)

## Duration / frame count

- FPS is fixed at **24**. Frame count must be on the **`17k + 5`** grid (min 5):
  `5, 22, 39, 56, 73, 90, 107, 124…`. Duration = `frames / 24`.
- Measured single-shot ceilings on 32 GB: **1344×768 → 209 f (8.71 s)** ·
  **1024×576 → 243 f (10.12 s)** · 1920×1088 → 39 f verified.
- Longer films = **chain shots**: the next shot's init frame (`-i <png>`) is the previous
  shot's last frame. Seams measured near-invisible; VRAM cost is just the sum of
  independent shots. Details in the guide.

## Corrections — what we got wrong at first (2026-09-29)

The first release of this repo (2026-09-07) recorded two conclusions we later overturned
by measurement. They stayed online for three weeks; this section is the honest fix. The
[history doc](docs/history/troubleshooting.md) keeps the originals with annotations.

1. **"`--offload-to-cpu` is wrong / extremely slow" — WRONG, and our own recommended
   command was the bug.** Explicit `--backend` / `--params-backend` assignments override
   `--offload-to-cpu` and disable `--auto-fit`, so with our old command we were neither
   offloading nor auto-placing. The official sd.cpp H3 example pairs
   `--diffusion-fa --offload-to-cpu`; the measured cost of offload vs weights-on-GPU is
   **+1.7%**, and weights-resident VRAM drops 16.5 GB → 0 MB.
2. **"ComfyUI cannot run H3 on V100" — PARTIALLY WRONG.** The default route
   (0.33.2 + comfy-kitchen + T8 + v100-patch) still fails, but a different route works:
   fp8_scaled DiT + nvfp4 encoders + the `ComfyUI-MiniMaxH3-FP16Safe` plugin + an
   eager-execution patch. T2V and I2V verified, same 209-frame ceiling at 768p. It runs
   3–6× slower than sd.cpp, so sd.cpp stays the production stack — but "impossible" was wrong.
3. Related lesson (not claimed in the first release, but worth recording): **an OOM is
   not a physics result.** Our largest single gain came from refusing to treat a
   "39-frame ceiling at 1024×576" as a hardware limit — it was the default attention
   kernel materializing the full attention matrix, and one flag (`--diffusion-fa`)
   removed it.
